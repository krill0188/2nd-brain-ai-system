## 2. 남은 구조적 문제

1. **한 번에 `--limit`건만 처리하는데, 검증은 대기 0건을 요구한다.** 신규 문서가 한 번에 10건을 넘으면 매번 같은 지점에서 실패한다.
2. **대기 문서가 발행 전체를 막는다.** `discovery` 그래프는 사람 검토 전 단계(발견 레이어)인데, 그 지연이 뉴스·브리핑 배포까지 막는다. 이번 정지의 본질적 원인이다.
3. **구독 쿼터 소진 같은 일시 장애도 같은 경로로 발행을 막는다.** 폴백을 금지했으므로 추출이 실패하면 대기가 남는다.
4. **실패 알림에 원인 정보가 부족하다.** 텔레그램은 "예기치 못한 오류 단계=derived"와 명령줄만 전달했다.

## 3. 설계안

### A. 대기 문서 소진 루프 (권장 1순위)

`Generate:discovery`가 한 번 호출로 끝나지 않고, 대기가 0이 되거나 예산이 다할 때까지 반복한다.

```
budget = 20분 (추출 단계 전용 벽시계 예산)
loop:
    run extract --limit 10
    pending = artifact-status 의 discovery_pending_documents
    if pending == 0: break
    if 이번 호출에서 성공 0건 (연속 실패): break   # 쿼터 소진 등
    if 예산 소진: break
```

- 신규 문서가 100건이어도 약 14초 × 100 = 약 23분으로, 예산 안에서 대부분 소진된다.
- 호출당 `--limit`을 작게 유지하므로 중간에 끊겨도 상태 파일은 호출 단위로 저장되어 이어서 진행된다.

### B. 검증을 두 등급으로 분리 (권장 2순위, A와 함께)

| 항목 | 현행 | 변경 |
|---|---|---|
| 중복 슬러그, 누락 노드, 불필요 노드, 노드 신선도 | 실패 시 발행 차단 | **유지** (공개 정합성) |
| `discovery_pending_documents` > 0 | 실패 시 발행 차단 | 소진 루프가 끝났는데도 남은 경우 **경고**로 강등, 텔레그램에 건수 표기 |
| 추출 실패(`failed`) 건수 | 검증 없음 | 실패율이 임계 이상이면 차단 |

근거: 발견 레이어의 지연은 공개 정합성 문제가 아니다. 정합성 오류와 지연을 같은 등급으로 두면 이번처럼 지연 하나로 뉴스 전체가 멈춘다. 이 부분은 판단이 필요한 변경이라 승인 대상이다.

### C. 단계 예산과 전체 제한 분리

- 현재 `--refresh-derived` 전체에 3600초 하나만 있다. 단계별 예산(추출 20분, 임베딩 N분 등)을 두고, 예산을 넘긴 단계의 이름을 실패 보고에 남긴다.
- 전체 제한 3600초는 유지하되 `TimeoutExpired` 대신 "어느 단계에서 몇 초 지났는지"를 기록한다.

### D. 실패 알림에 원인과 다음 명령 포함

`auto-publish.py`의 실패 알림을 아래 형식으로 바꾼다.

```
[2nd 자동발행] 실패 단계=derived / 세부=Generate:discovery
원인: 시간 초과(3600초) — 직전 단계 소요: 추출 58분
조치: <단계별 정해진 한 줄 안내>
재실행: cd ~/2nd && python3 scripts/with-pipeline-lock.py -- .venv/bin/python scripts/auto-publish.py --apply
```

### E. 사전 점검 `--doctor`

`auto-publish.py --doctor`가 배포 없이 전 단계 사전 조건을 읽기 전용으로 점검한다.

- 커밋되지 않은 승인 파일, 레거시 launchd 겹침, 락 점유, 대기 문서 건수, 쿼터 상태, 웹 저장소 동기화
- 실패 항목마다 원인과 조치 한 줄을 출력한다.
- 이번에 하나씩 겪은 막힘(미커밋 승인 파일, 레거시 겹침, 락, 대기 문서)을 한 번에 사전 발견한다.
