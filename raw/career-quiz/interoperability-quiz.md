### Q51. STANAG 4586 LOI(상호운용성 수준) 5단계 중 LOI 1과 LOI 5는?
- ✅ LOI 1: 간접 수신, LOI 5: 완전 제어
-    LOI 1: 완전 제어, LOI 5: 간접 수신
-    둘 다 동일
-    LOI는 3단계

**해설**: LOI 1: 간접적 데이터 수신만. LOI 2: 직접 데이터 수신. LOI 3: 페이로드 제어. LOI 4: 비행 제어. LOI 5: 이착륙 포함 완전 제어.

**팁**: 각 LOI 수준에서 필요한 기술적 요구사항(데이터링크, 프로토콜)을 설명하세요.

### Q52. 이기종 GCS 통합의 핵심 아키텍처는?
- ✅ Protocol Abstraction Layer
-    직접 연결
-    USB 케이블
-    없음

**해설**: Protocol Abstraction Layer(프로토콜 추상화 계층)를 두어 MAVLink, STANAG 4586 등 다양한 프로토콜을 공통 인터페이스로 변환합니다.

**팁**: 실제 추상화 레이어 설계 경험, 어댑터 패턴 적용 사례를 구체적으로 설명하세요.

### Q53. 상호운용성 시험(IOTEST)의 목적은?

-    속도 측정
-    비용 절감
-    디자인 검증

**해설**: IOTEST는 서로 다른 체계(GCS-UAV, C4I-UAS 등) 간 데이터 교환, 명령 전달 등 연동 기능이 정상 동작하는지 검증하는 시험입니다.

**팁**: IOTEST 계획 수립, 시험 항목 설계, 결과 분석 경험을 구체적으로 준비하세요.

### Q54. MAVLink과 STANAG 4586의 차이는?
- ✅ MAVLink: 경량 오픈소스, STANAG: NATO 군용 표준
-    같은 프로토콜
-    STANAG이 더 가벼움
-    MAVLink이 군용

**해설**: MAVLink: 가볍고 오픈소스, 상용/연구용 드론에 널리 사용. STANAG 4586: NATO 군용 표준, 무겁지만 상호운용성 보장.

**팁**: 두 프로토콜의 브릿지(변환 레이어) 설계 경험이 있으면 큰 차별점입니다.

### Q55. OMS(Open Mission Systems) 아키텍처란?
- ✅ 미국 공군 개방형 미션 시스템 표준

-    온라인 관리 서비스
-    없음

**팁**: MOSA(Modular Open Systems Approach)와 연계하여 한국 국방 적용 가능성을 논하세요.

### Q56. ROS2-MAVLink 브릿지 구현 방법은?

**팁**: microDDS(XRCE-DDS)의 실시간 성능과 ROS2 토픽 매핑 경험을 설명하세요.

### Q57. UTM(UAS Traffic Management)이란?
- ✅ 무인기 공역 통합 관리 시스템
-    대학 교통 관리
-    통합 테스트 관리
-    없음

**해설**: UTM은 저고도 무인기의 안전한 공역 운용을 위한 교통 관리 시스템입니다. 비행 계획, 실시간 추적, 충돌 회피 서비스를 제공합니다.

**팁**: NASA UTM, K-UTM 등 국내외 UTM 개발 현황과 군용 드론과의 연계 방안을 논하세요.

### Q58. 상호운용성 성숙도 모델(LISI)의 최고 수준은?
- ✅ 레벨 4: 기업 수준 통합
-    레벨 2
-    레벨 6
-    레벨 10

**해설**: LISI(Levels of Information Systems Interoperability): 레벨 0(고립)→1(연결)→2(기능)→3(도메인)→4(기업 수준 통합). 최고는 레벨 4.

**팁**: 현재 한국군 UAS 상호운용성이 어느 레벨인지, 목표 레벨과 달성 전략을 논하세요.

### Q59. SDR(Software Defined Radio)의 프로토콜 유연성이란?
- ✅ SW로 통신 프로토콜 변경 가능
-    하드웨어 교체 필요
-    불가능
-    주파수 변경만 가능

**해설**: SDR은 소프트웨어로 변/복조, 필터링, 프로토콜 처리를 수행하여, 하드웨어 변경 없이 다양한 통신 프로토콜을 지원합니다.

**팁**: SDR을 이용한 이기종 드론 통합 통신의 실제 적용 사례를 준비하세요.

### Q60. CoT(Cursor on Target)의 역할은?
- ✅ 위치 정보 공유 표준 포맷 (XML 기반)
-    카서 제어

-    데이터베이스

**해설**: CoT는 위치 정보(누가, 어디서, 언제)를 XML 형식으로 표준화하여 다양한 군사 시스템 간 실시간 위치 공유를 가능하게 합니다.

**팁**: ATAK(Android TAK)에서의 CoT 활용과 드론 ISR 데이터 연동을 설명하세요.

### Q76. DDS(Data Distribution Service)를 드론에 적용하는 이유는?
- ✅ 실시간 pub/sub, QoS 보장, 자동 디스커버리
-    가격이 저렴
-    설치가 쉬움
-    MAVLink 대체 불가

**해설**: DDS는 실시간 pub/sub 미들웨어로, QoS 정책(지연, 신뢰성, 대역폭), 자동 디스커버리, 분산 아키텍처를 지원합니다. ROS2의 기반 통신.

**팁**: DDS의 QoS 프로파일(Reliable vs Best Effort, History Depth 등) 설정 경험을 설명하세요.

### Q411. 상호운용성(Interoperability)의 가장 기본적인 정의는 무엇인가?
- ✅ 서로 다른 시스템이나 장치가 정보를 교환하고 그 정보를 활용할 수 있는 능력
-    동일 제조사의 장비끼리 통신하는 능력
-    하나의 시스템이 여러 프로토콜을 동시에 처리하는 능력
-    소프트웨어를 다양한 운영체제에서 실행하는 능력

**해설**: 상호운용성은 이기종 시스템 간에 데이터를 교환하고, 교환된 정보를 의미 있게 활용할 수 있는 능력을 뜻합니다. 단순 통신을 넘어 의미 공유까지 포함합니다.

**팁**: Interoperability = 정보 교환(Exchange) + 활용(Use) 두 가지를 모두 포함

### Q412. 상호운용성의 3가지 수준을 올바르게 나열한 것은?
- ✅ 구문적(Syntactic) → 의미적(Semantic) → 운영적(Operational)
-    물리적(Physical) → 논리적(Logical) → 응용적(Application)
-    데이터(Data) → 서비스(Service) → 프로세스(Process)
-    하드웨어 → 소프트웨어 → 네트워크

**해설**: 상호운용성은 구문적(데이터 형식), 의미적(데이터 의미), 운영적(프로세스·절차) 3단계로 구분됩니다. 구문적 수준이 가장 낮고, 운영적 수준이 가장 높습니다.

**팁**: 구문(Syntax) → 의미(Semantic) → 운영(Operational) 순서로 복잡도 증가

### Q413. NATO STANAG 4586은 무엇을 정의하는 규격인가?
- ✅ 무인항공기 통제 시스템(UCS)과 지상 제어 장비 간의 표준 인터페이스
-    NATO 회원국 간의 암호화 통신 프로토콜
-    드론 배터리 충전 표준 규격
-    무인기 탑재 센서의 해상도 및 성능 기준

**해설**: STANAG 4586은 UCS(Unmanned Control System)와 UAV 간, 또는 UCS와 지상 장비 간 표준 인터페이스를 정의합니다. 이를 통해 다국적 군 환경에서 이기종 UAV를 단일 GCS로 통제할 수 있습니다.

**팁**: STANAG 4586 = UCS 표준 인터페이스, 이기종 UAV 통합 운용의 핵심

### Q414. REST API의 주요 특징 중 상호운용성 관점에서 가장 중요한 것은?
- ✅ 무상태성(Stateless)과 표준 HTTP 메서드 사용으로 플랫폼 독립적 통신 가능
-    바이너리 직렬화로 전송 속도가 빠름
-    실시간 양방향 통신을 지원함
-    XML만 사용하여 데이터를 표현함

**해설**: REST API는 HTTP 표준을 기반으로 하며 무상태성 특성 덕분에 언어, 플랫폼에 무관하게 모든 시스템이 통신할 수 있어 상호운용성이 높습니다.

**팁**: REST = HTTP 기반 + 무상태 + 플랫폼 독립 → 상호운용성 최고

### Q415. UTM(Unmanned Traffic Management)에서 상호운용성이 요구되는 주된 이유는?
- ✅ 다양한 제조사와 운영자의 드론이 같은 공역에서 안전하게 비행하려면 공통 데이터 형식과 통신 규약이 필요하기 때문
-    드론의 배터리 수명을 연장하기 위해
-    GPS 정확도를 향상시키기 위해
-    드론 가격을 표준화하기 위해

**해설**: UTM에서는 항공교통관리(ATM) 시스템, 다양한 드론 운영자, 기상 서비스, 지도 서비스 등이 연동되어야 합니다. 이기종 시스템 간 공통 인터페이스 없이는 안전한 공역 관리가 불가능합니다.

**팁**: UTM 상호운용성 = 공역 안전 관리의 전제 조건

### Q416. JSON-LD(JSON for Linked Data)가 일반 JSON보다 상호운용성이 높은 이유는?
- ✅ 데이터에 의미(Semantic)와 컨텍스트를 부여하여 다른 시스템이 데이터의 뜻을 자동으로 해석할 수 있기 때문
-    파일 크기가 더 작기 때문
-    암호화가 내장되어 있기 때문
-    실시간 스트리밍을 지원하기 때문

**해설**: JSON-LD는 @context를 사용해 데이터 필드에 URI로 정의된 의미를 연결합니다. 이를 통해 서로 다른 시스템이 같은 단어를 다른 의미로 해석하는 문제를 방지합니다.

**팁**: JSON-LD = JSON + @context → 의미적 상호운용성 달성

### Q417. OAuth 2.0이 드론 시스템 상호운용성에서 주로 사용되는 목적은?
- ✅ 제3자 시스템이 사용자 자격증명 없이도 안전하게 API에 접근할 수 있도록 인증/인가 위임
-    드론 간 암호화된 영상 전송
-    GPS 좌표 암호화
-    비행 계획서 전자 서명

**해설**: OAuth 2.0은 토큰 기반 위임 인가 프레임워크입니다. UTM, UAS 서비스 공급자, 운영자 앱 등이 서로 다른 주체일 때 안전하게 API를 공유하는 데 사용됩니다.

**팁**: OAuth 2.0 = 위임 인가(Delegated Authorization), 비밀번호 공유 없이 API 접근

### Q418. DDS(Data Distribution Service)가 드론 시스템에서 사용될 때의 주요 장점은?
- ✅ 발행-구독(Pub-Sub) 모델로 분산 시스템 간 실시간 데이터 공유가 가능하며 미들웨어 이기종성을 극복함
-    단일 서버에 모든 데이터를 중앙 집중화함
-    HTTP 기반으로 웹 브라우저와 호환됨
-    배터리 소모를 최소화하는 저전력 프로토콜

**해설**: DDS는 OMG 표준 미들웨어로 PX4, ROS2 등에서 사용됩니다. 브로커 없이 P2P 발행-구독이 가능하며 QoS 설정으로 실시간성을 보장합니다.

**팁**: DDS = ROS2 기본 미들웨어, 브로커리스 P2P Pub-Sub

### Q419. MOSA(Modular Open Systems Approach)의 핵심 목표는?
- ✅ 시스템을 독립적인 모듈로 설계하여 특정 벤더 종속 없이 구성 요소를 교체·업그레이드 가능하게 함
-    모든 소프트웨어를 오픈소스로 공개함
-    하드웨어 비용을 최소화함
-    시스템 개발 속도를 극대화함

**해설**: MOSA는 미국 DoD가 추진하는 조달 방침으로, 개방형 표준 기반 모듈화 설계를 통해 공급업체 종속(Vendor Lock-in)을 방지하고 시스템 수명주기 비용을 낮추는 것이 목표입니다.

**팁**: MOSA = 벤더 종속 탈피 + 모듈 교체 자유 = 미국 DoD 조달 원칙

### Q420. SOSA(Sensor Open Systems Architecture)가 달성하고자 하는 것은?
- ✅ 다양한 센서 모듈이 표준 슬롯 인터페이스를 통해 서로 다른 플랫폼에 호환되도록 하는 개방형 센서 아키텍처
-    센서 데이터를 클라우드에만 저장하는 아키텍처
-    단일 제조사 센서만 사용하는 폐쇄형 아키텍처
-    센서 비용을 낮추기 위한 저사양 표준화

### Q456. 프로토콜 버퍼(Protocol Buffers, Protobuf) v2와 v3의 상호운용성 차이에서 가장 주의해야 할 점은?
- ✅ v3에서 required 필드가 제거되어 v2 required 필드를 사용하는 서비스와 v3 클라이언트 간 상호운용 시 필드 누락으로 역직렬화 오류 발생 가능
-    v3는 unknown 필드를 기본 보존하므로 v2 서비스가 정의하지 않은 확장 필드를 v3 클라이언트가 추가하면 역방향 직렬화 시 데이터 손실 없이 투명하게 전달
-    v3에서 기본값이 0/false/빈문자열인 필드는 직렬화 시 생략되어 v2 클라이언트가 해당 필드를 명시적 기본값으로 설정한 경우와 구분이 불가능

**팁**: Protobuf v3 = required 제거, v2 required 필드와 혼용 시 오류 주의
